# 链式代理(前置 → 落地)

链式代理让一个节点**先经由另一个节点拨号**:本机到"落地(出口)"节点的连接,先由"前置(第一跳)"
节点建立。典型用法是用一台便宜的直连中转机当第一跳,把落地放在落地机/家宽上,落地机的地址不必
公网可达,也不需要在本机上暴露。

```
本机 ──直连──> 前置(第一跳) ──> 落地(出口) ──> 目标网站
```

## 怎么配

面板 →「分流」→「链式代理」卡片:

1. **落地(出口)**:选一个节点——它是实际出网的那一跳,流量最终从它的 IP 出去。
2. **前置(第一跳)**:选一个节点或策略组——它必须是**本机能直连**的那一跳。选策略组时,
   组里的成员会被当成候选(例如按地区自动生成的组)。
3. 保存后到页面顶部点「立即部署」,内核会按新配置重启,链路生效。

一条链路一个落地:同一个节点只能有一个前置(节点只能有一个上游)。想去掉链路,点该行的删除。

## 生效与不生效

生成配置时面板会逐条校验,下面几种情况**这条链路会被丢掉**并在卡片上标出来:

| 情况 | 结果 |
| --- | --- |
| 落地/前置的节点已经不存在(订阅刷新、改名、被禁用) | 不生成 detour |
| 前置是"包含落地自己"的策略组(比如默认那个收全部节点的自动组) | 不生成 detour,否则内核启动即 `circular outbound dependency` |
| 两条链路互相咬住、或绕几跳绕回自己 | 后一条不生成 |
| 落地选的是策略组 | 不生成(sing-box 的 selector/urltest 不接受 detour 字段,写进配置会直接 `unknown field`) |

**为什么必须由面板来拦:** sing-box 的 `check` 不校验 `detour` 的目标是否存在、也不校验成环——
这两种配置都能"校验通过",直到内核启动时才 FATAL:

```
start service: dependency[nope] not found for outbound[落地]
start service: circular outbound dependency: 落地 -> PROXY -> 落地
```

所以面板在生成配置时就按当前真实存在的节点/组解算链路,把落地不了的条目丢掉(见
`panel/server/engine/chain.mjs`)。**"配置能过 check"不代表链路是对的。**

## 订阅里自带的链路

- Clash(Meta)订阅里的 `dialer-proxy` 与 sing-box 的 `detour` 语义一致,会被原样收下
  (`panel/server/engine/clash.mjs`)。
- sing-box JSON 订阅里 outbound 的 `detour` 同样保留(`panel/server/engine/singbox-in.mjs`)。

两者的目标写的都是订阅里的原始节点名,而面板会按地区/特征**重命名节点**,所以名字对不上时
这条链路会被当作"前置不存在"丢掉——需要在「链式代理」卡片里手动再配一条。

## 局限

- 前置与落地都只能是本机识别到的节点/组;不支持"多级链"以外的其它拓扑(链就是线性的)。
- 链路上每一跳的协议都要自己可用:本机会分别对每个节点测速/测延迟,测的是"本机直连该节点",
  不代表"经由前置连该节点"的延迟。
- wireguard 节点以 endpoint 形式生成,同样可以当前置或落地(实测 `detour` 字段被接受)。
